# Bounded Improvement

Read only for an identified reusable reasoning/process failure or a proposed
rule change. Do not append reflection to every task or audit unrelated rules.

## Locate Before Adding

Identify the failed stage and distinguish:

| Failure | First remedy to evaluate |
|---|---|
| Existing instruction was not loaded | Trigger/routing repair |
| Loaded instruction is ambiguous, conflicting, or duplicated | Rewrite, merge, or remove redundancy |
| Evidence or tools cannot support the decision | Improve observation/capability or state the limit |
| Verification missed the failure | Repair the oracle, case, or coverage |
| A reusable constraint is genuinely missing | Consider a new rule at the narrowest applicable scope |

Recurrence raises priority, not automatic authority for a global rule. One
severe event may justify evaluation; do not wait for an arbitrary count.

## Propose, Test, Retain Or Withdraw

1. Explain the mechanism, why existing controls are insufficient, and the
   smallest useful change. Compare adding with modifying, merging, removing,
   or repairing tools/routing. Do not weaken safety to reduce word count.
2. Define intended benefit, scope, evidence needed, and withdrawal/revision
   criteria before testing. Diagnose the original failure; do not encode its
   incidental wording as a universal rule.
3. Replay the original case, then a new relevant case and an ordinary task that
   should stay unaffected. Compare decision quality, false claims, coverage,
   appropriate stopping, extra reads/questions, and time where measured.
4. Retain only the supported scope. If the change misses the failure, harms
   normal work, duplicates an effective control, or adds cost without benefit,
   revise, narrow, or withdraw it through the applicable authorized workflow.
   One replay does not prove transfer; a passing baseline is not an improvement.

Once the bounded acceptance is met, stop. Reopen only for new evidence, changes,
or a relevant failure; no recursive skill-upgrading loop. Updating rules,
knowledge, or memory requires existing user authorization; this reference grants
none and does not claim model retraining. Keep maintenance evaluation outside
the normal task workflow, and report untested transfer as untested.
